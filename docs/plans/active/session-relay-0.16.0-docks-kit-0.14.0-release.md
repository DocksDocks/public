# Release docks-kit 0.14.0 with Relay 0.16.0

## Goal

After the Docks parent staged the Session Relay 0.16.0 three-asset prerelease, independently re-verify and pin its three native binary SHA-256 digests, remove the retired `x86_64-apple-darwin` target from the closed Session Relay manifest contract, bump docks-kit from 0.13.0 to 0.14.0, update every current published pin surface and hardcoded expectation, regenerate the generated payload and recorder-owned goldens, pass the full local gate, release tag `cli-v0.14.0` plus npm `docks-kit@0.14.0` through the existing OIDC workflow, then finish and archive a remotely readable public child for the Docks parent.

## Context & rationale

This is the child half of the cross-repository Session Relay 0.16.0 release. The parent run in repository `DocksDocks/docks` (plan `docs/plans/active/session-relay-0.16.0-release.md`) carries `goal_id` `cef66d21-5bd3-4e07-a0e8-e393822dcfb0` and `run_id` `1c5b6f71-c69d-4566-adcc-4c15a9f0c599`. This child run shares the same `goal_id` under a distinct `run_id`, per one-child-run-per-repository joined by `goal_id`.

Parent facts fixed before this plan was drafted, never re-derived here: tag `session-relay--v0.16.0` exists in `DocksDocks/docks`; its GitHub prerelease is staged with exactly three binaries plus `SHA256SUMS`; Intel macOS (`x86_64-apple-darwin`) is retired as of Session Relay 0.16.0 and must be removed from the pin, not carried forward. The staged digests are:

- `aarch64-apple-darwin` — `da8b114216c3f2301ad582df8e59b49e91953abcc1112b510466b31637fda825`
- `aarch64-unknown-linux-musl` — `816b6b8bd2d2c2518ea359a5a21502213347b387a1cc576a0fb9cf541e5646ed`
- `x86_64-unknown-linux-musl` — `b3ca082dc5ea51e8322be407cdb4bbcaaa05d80bd62c3553f82ab98c1a95498a`

The parent's acceptance reads this child back mechanically from `DocksDocks/public@main` by parsing, not substring matching. To satisfy it, this plan keeps the exact slug `session-relay-0.16.0-docks-kit-0.14.0-release`: the parent requires exactly one file under `docs/plans/finished/` ending `-session-relay-0.16.0-docks-kit-0.14.0-release.md`, whose record's `plan_path` is exactly `docs/plans/active/session-relay-0.16.0-docks-kit-0.14.0-release.md`, shared `goal_id`, distinct `run_id`, both review phases `passed`, frontmatter `status: finished` with non-null `finished_at`, a 40-hex `implementation_commit` whose committed `SoT/toolchain.json` pin has `verified` 0.16.0, `tag` `session-relay--v0.16.0`, `plugin_version` 0.16.0, `repository` `DocksDocks/docks`, `policy` `exact`, and an assets map that is exactly the three name-to-digest pairs above; tag `cli-v0.14.0` containing that commit; and npm SLSA provenance for `docks-kit@0.14.0` naming subject `pkg:npm/docks-kit@0.14.0`, workflow repository `https://github.com/DocksDocks/public`, and workflow path `.github/workflows/release-cli.yml`.

### Closed three-target pin cutover {mechanism}

`SoT/toolchain.json` is data; enforcement lives in `cli/src/engine-native/sessionRelayCli.ts`. `parseSessionRelayManifest` rejects any manifest whose assets keys are not exactly the `TARGETS` tuple, and `installSessionRelayCli` requires committed digest = same-release `SHA256SUMS` row = downloaded bytes before an atomic rename, so after this cutover a four-asset pin, a retained Intel digest, or a `darwin`/`x64` install attempt all fail closed before touching `~/.local/bin/session-relay`. The generated payload embeds the toolchain bytes, so `cli/src/generated/sotPayload.ts` must be regenerated through its generator, and both goldens re-recorded through their recorders, or `bun run check:generated` and the golden gates fail. docks-kit's own release matrix is a separate contract and keeps four `docks-kit-*` binaries plus `SHA256SUMS`; only the Session Relay pin loses Intel macOS.

## Environment & how-to-run

Run every command from this repository's root. Required tools: Bun (the `./docks-kit` launcher bootstraps it), Node, Git, and `gh` for the probe/release boundaries.

- Payload: regenerate with `bun cli/scripts/generate-sot-payload.ts`; verify with `bun run check:generated`.
- Goldens: update only with `bun cli/test/golden-dryrun.ts --update-goldens` and `bun cli/test/golden-mutation.ts --update-goldens`; verify normal and `--prove-red` modes afterward.
- Full local gate: `bun run test:ci` (generated freshness, typecheck, unit, POSIX runtime smoke, both goldens).
- User-facing smoke: `./docks-kit sync claude codex --dry-run --skip-rtk` and `./docks-kit sync agents --dry-run --skip-rtk`.
- Release: pushing the exact tag `cli-v0.14.0` triggers `.github/workflows/release-cli.yml`; expected GitHub assets are exactly four docks-kit Linux/macOS x64/arm64 binaries plus `SHA256SUMS`, and npm publication is `docks-kit@0.14.0` with OIDC provenance only. Never add a token fallback.
- Lifecycle tooling lives in repository `DocksDocks/docks` under `plugins/plan-lifecycle/skills/productivity/plan-manager/scripts/` (`plan-run.mjs`, `lifecycle/plan-self-check.mjs`, `lifecycle/dispatch-review.mjs`); every driver takes this repository's root via `--repo`.
- Before A9, A10, A11, A12, and A14, export `EXECUTION_PARENT` and `IMPLEMENTATION_COMMIT` from the installed current PlanRunV1 after the implementation checkpoint; never retype either SHA from memory. A13 needs no exported identity.
- Archive: move only at finish to `docs/plans/finished/<finish-date>-session-relay-0.16.0-docks-kit-0.14.0-release.md`, where `<finish-date>` is the UTC date of the archive transaction.

`requested_effects` records intent only and is never live authority. Every non-local row requires a fresh `ExternalAuthorityV1` derived from the operator's exact current message at execution time, matching that row's exact effect, mode, and target. `probe` is read-only. Because pushing `cli-v0.14.0` triggers both the GitHub release and npm publication, matching live `release` and `publish` authorities must both exist before the tag boundary.
