## Goal

The packed-tarball proof states only the guarantee it enforces, and tag cli-v0.15.5 publishes that corrected release path.

At creation two commits sat unpushed on top of the published 0.15.4: `c435775`,
which added the packed-content proof to the release workflow, and `be50faf`,
which archived that release's record. Review round three had narrowed the
proof's guarantee to content equality for every unpacked file, while the
workflow's own success summary still claimed the archive itself was identical.
The claim was repaired before the commits left this machine, and the repaired
path was then published, because a release proof that overstates itself is worse
than one that states less. The rebuild replaced those two hashes with `18d6639`
and `fe62f67`, and the release commit `98eafbf` sits on top of them.

Mode: plan-and-implement

## Research

Repository facts verified by reading:

- `.github/workflows/release-cli.yml:213-214` prints `tarball identical to %s
  across %d packed files`. The step's three checks establish something narrower.
  Check 1 at lines 161-166 compares the working tree with HEAD across the
  declared roots. Check 2 at lines 170-174 compares HEAD with the tag across
  those same roots. Check 3 at lines 176-211 does the work the summary line
  names: it rebuilds the member list from the unpacked tarball, lets
  `git archive` reject any packed path that does not exist at the tag, then
  compares each unpacked file's content with the tag's through `diff -r`.
  Content of every unpacked file is therefore proved; archive-level properties
  of the tarball itself — member order, duplicate members, file modes — are not,
  because `diff -r` reads content and the member list is sorted before use.
  `CHANGELOG.md:5-10` and the archived record were already narrowed to per file
  content equality in `c435775`; this line was missed.
- `.github/workflows/release-cli.yml:14-16` says the dispatch path proves every
  packaged file is byte-identical to the tag's tree. That sentence is per file,
  which `diff -r` does establish byte-wise, so it stays.
- The version literal is authored in exactly two places, `package.json:3` and
  the release prose at `README.md:139`.
  `cli/src/generated/sotPayload.ts:4` carries the same literal as
  `GENERATED_PACKAGE_VERSION` but is regenerated from the manifest, never
  hand-edited. `CHANGELOG.md` carries no version literal: its release surface is
  the dated topic heading. At creation `CHANGELOG.md:3` held an `## Unreleased`
  section describing the proof step, and `step:release_prep` replaced it with the
  dated heading that line 3 holds now:
  `## 2026-08-21 — Release proof states only the guarantee it enforces`
- Both commits are unpushed: `git log --oneline -3` shows `be50faf`, `c435775`,
  then the published `e343c1b`. Rebuilding them rewrites no published history,
  so the summary repair belongs inside `c435775` rather than in a follow-up
  commit that would ship a wrong sentence to `main` and correct it later.
- Rebuilding `c435775` changes its hash, and the archived record cites that hash
  three times as the fix commit for the round-one and round-two defects. Those
  citations are part of `be50faf`, the child commit, so both are rebuilt in one
  operation and the citations updated to the new hash before the push.
- Bun stays at the version this kit already targets: `SoT/toolchain.json` pins
  `bun` `floor` and `verified` at `1.4.0`, and
  `.github/actions/setup-bun-cache/action.yml:8` is the single CI declaration of
  it. This release changes no toolchain pin.
