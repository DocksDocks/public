## Goal

The kit pins, launchers, CI, runtime, tests, and docs all target Bun 1.4.0 with a v2 lockfile, a green full-scope blocking audit gate, and a parallelized local gate.

Bun 1.4.0 shipped on 2026-08-20. The kit pinned 1.3.14, so every managed install, CI job, and golden expectation still targeted the previous runtime. The release also removes a private-path heuristic the kit relied on and changes lockfile, audit, parser, and compile behavior, so the bump is a cross-subsystem change rather than a literal substitution.

Mode: plan-and-implement

## Research

Hypothesis: the Bun pin is a single-source value, so the upgrade is a literal bump plus regeneration. **Refuted.** The pin is single-source, but 1.4.0 also changes runtime API surface, lockfile format, audit exit status, TOML parsing strictness, and compile-time config loading, and the repository carries pin consumers and behavioral gates that regeneration does not reach.

Repository facts verified by reading:

- `SoT/toolchain.json` is the sole authored Bun pin: the `bun` entry carried `kind: managed`, `policy: present`, `floor` and `verified` both `1.3.14`, and `pinnable: true`.
- `cli/scripts/generate-sot-payload.ts` owns the derived pins. Its `BUN_PIN_START` / `BUN_PIN_END` markers and `renderBashBunPin` / `renderPowerShellBunPin` functions rewrite one marked assignment in each of `docks-kit`, `docks-kit.ps1`, `install.sh`, and `install.ps1`, and it emits `cli/src/generated/sotPayload.ts`. These five files are generated output and must never be hand-edited.
- `cli/test/unit/hostTargets.test.ts` asserts the four generated pin assignments, and `cli/test/unit/payload.test.ts` proves the generator's staleness gate by rewriting a `BUN_PIN` value and expecting exit 1. Both read the pin from the manifest rather than a literal, so regeneration plus the acceptance commands covers them.
- `cli/src/engine.ts` exported `compiled` as `process.argv[1].startsWith("/$bunfs/")`. `cli/src/commands/update.ts` `updateCheckout` and `cli/src/engine.ts` `engineCapture` are its only production readers; both consume the boolean alone.
- `cli/src/kitHome.ts` receives `moduleDir` as an injected value and `cli/test/unit/kitHome.test.ts` passes the `/$bunfs/root` string into it. That is a dependency-injection seam for testability, not a runtime heuristic, so it stays.
- **Corrected claim.** Product code calls no TOML, JSONC, or YAML parser, and `cli/src/engine-native/codexToml.ts` stays line-based to preserve comments and user content. The test suite does exercise the parser: `cli/test/unit/codexTomlMerge.test.ts` `expectTomlToParse` spawns `bun -e "Bun.TOML.parse(await Bun.stdin.text())"` and three cases call it against the deployed Codex config. Bun 1.4 rewrote `Bun.TOML` for TOML v1.1, so it now throws `SyntaxError` instead of `BuildMessage` and rejects duplicate keys. That makes this test a stricter gate on merged Codex output under 1.4, and the unit gate is the place it surfaces.
- `cli/test/lib/goldenResources.ts` `temporaryDir` allocates each harness home with `mkdtempSync` plus a sibling owner-PID marker. `sweepStaleTemporaryDirs` skips any directory whose owner PID is the current process or is still alive via `processIsAlive`, falling back to `STALE_TEMP_DIR_AGE_MS` only when the marker is unreadable. Concurrent golden runners therefore cannot delete each other's homes.
- `cli/test/statusline-runtime-smoke.mjs` is the only timing-sensitive leg. It enforces a direct-Bun p95 ceiling and a posix median ceiling of 250 ms, and its own comment records that p95 "flakes on shared CI" under load. A grep of `cli/test/unit` for `p95`, `performance.now`, `elapsed`, and `ceiling` found no wall-clock assertion, so `test:unit` is not timing-sensitive and may run inside the parallel group.
- **Corrected claim.** `.github/workflows/parity.yml` declares four jobs: `lint`, `portable`, `golden-dryrun`, and `golden-mutation`. There is no `quality` job. `lint` runs pinned actionlint only and installs no dependencies. `portable` is a matrix over `ubuntu-24.04`, `macos-26`, and `windows-2025` and owns dependency install, the payload freshness check, typecheck, unit tests, the runtime smoke, and `smoke:native`. Job-level parallelism therefore already exists in CI, so `bun run --parallel` only shortens the local chain.
- `.github/actions/setup-bun-cache/action.yml` was the only workflow-side Bun version, appearing once as `bun-version` and twice in the cache key and restore key.
- **New finding.** `docks-kit` `find_bun` returns the first Bun found on `PATH`, `BUN_INSTALL/bin`, or `~/.local/bin` with no version comparison, and the launcher then runs `bun install --frozen-lockfile` when `node_modules/effect` is absent. `docks-kit.ps1` mirrors this. With `policy: present` the kit never auto-upgrades an existing Bun, so a contributor on 1.3.x reaches a v2 lockfile and fails inside `bun install` with a parse error that names neither the cause nor the remedy.

External facts verified against primary sources:

- Bun 1.4.0 release notes, https://bun.com/blog/bun-v1.4 — Rust rewrite, Node.js 26.3.0 compatibility target, `bun run --parallel`, `bun test --parallel`, `bun audit fix`, `bun dedupe`, `bun prune`.
- Official breaking-change list, https://github.com/oven-sh/bun/issues/28792 — `Bun.isStandaloneExecutable` is new additive public API (PR 32583); `bun.lock` defaults to `lockfileVersion: 2` while existing v0/v1 lockfiles still load, and older Bun cannot read v2; `Bun.TOML` was rewritten for TOML v1.1 conformance, throwing `SyntaxError` and rejecting duplicate keys (PR 32953); `bun build --compile` executables no longer auto-load `tsconfig.json` or `package.json` from the working directory (PR 25340); x64 builds are baseline-only (PR 34782); `Temporal` is enabled by default; lockfiles using the new nested or version-scoped overrides are written as `lockfileVersion: 3`, so this plan uses no such override.
- `node_modules/bun-types/bun.d.ts` declares `const isStandaloneExecutable: boolean`, so the API is typed once `@types/bun` is on the 1.4 line.
- `bun audit` on this checkout exits 1 with four advisories, three high and one moderate, in `nanoid` 3.3.15 and `postcss` 8.5.16, both reached only through `vitest > @vitest/mocker > vite > postcss`. `bun audit --omit dev` reports no vulnerabilities across 20 packages. `bun audit fix --dry-run` reports it would raise `nanoid` to 3.3.18 and `postcss` to 8.5.23, fixing all four inside the existing caret ranges without touching the pinned `vitest` 4.1.10 that the `@effect/vitest` peer range requires.
- **New finding, measured on the installed 1.4.0, then corrected by reading the upstream implementation.** Version 2 is not a different serialization. Bun PR 31539 (https://github.com/oven-sh/bun/pull/31539) adds `Version::V2`, switches `Version::CURRENT` to it, and gates two parse-time rejections behind `at_least(Version::V2)`: an off-registry npm tarball URL must carry a supported integrity hash, and a git `.bun-tag` must be a safe single path component. A v1 lockfile is therefore already a valid v2 lockfile whenever every entry satisfies both checks. This repository's `bun.lock` holds 134 entries, every one resolved from the default registry with a `sha512` integrity hash and none resolved from git, a file, or a URL, so it satisfies both gates.
- **Why no flag migrates it.** The same PR added `Stringifier::version_to_write`, which stamps v2 only when every package is v2-valid and otherwise keeps v1, so the stamped version travels with the data rather than with the writer. Bun never reaches that code here because it does not rewrite a lockfile already in sync with `package.json`: measured on three disposable copies, `bun install`, `bun install --lockfile-only`, and `bun install --force` each left the file byte-identical. Deleting the lockfile does produce v2, but it re-resolves every range. Measured drift was `vite` 7.3.6 to 8.2.2 with `rollup` replaced by `rolldown`, `esbuild` dropped, `lightningcss` added, and `@effect/platform-node-shared` moved from rc.109 to rc.111. That is a supply-chain event against a repository whose stance is to pin and never float, so regeneration is rejected as the migration path.
- **Migration chosen.** Set the version field to 2 in place. Proven on a disposable copy before the repository copy: the diff is one line, `bun install --frozen-lockfile` exits 0 against the v2 file, `bun pm ls --all` is identical before and after, a clean-slate reinstall from the v2 lockfile exits 0, and a later legitimate write keeps v2 rather than reverting it.
- **New finding.** `SoT/toolchain.json` gives the `bun` entry both `floor` and `verified`, and `cli/docs/toolchain.md` defines them as different things: `floor` is the minimum acceptable version, `verified` is the last kit-tested version and the exact pin for kit-driven installs. The generator's existing `BUN_PIN` carries `verified`, and its only consumer is the `bun-v$BUN_PIN` install tag. The two are equal at 1.4.0 today but are maintained independently, and the manifest's own comment directs maintainers to bump `verified` after testing a new release. A rejection gate compared against `BUN_PIN` would reject an at-or-above-floor runtime after the next verified-only bump, so the floor must be generated as its own value.

Durable fix chosen over the temporary one: replace the `/$bunfs/` private-path string test in `cli/src/engine.ts` with the official `Bun.isStandaloneExecutable` predicate, rather than keeping the heuristic and widening it for new compile targets.

Scope note recorded for the reviewer: step:toolchain_pin, step:test_literals, step:ci_bun_pin, step:types_and_api, and step:docs_pin were implemented before this plan existed, because the work began as a direct implementation and was correctly redirected to the canonical lifecycle mid-flight. Their diffs are real and are verified by this plan's acceptance commands rather than trusted.
